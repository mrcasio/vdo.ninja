# Build and runtime configuration

From a checkout of this release, run `./deployment/prepare-frontend.sh`, then `cd deployment` and `docker compose build`. The containers use the same isolated network and resource limits as the deployment; ports are not published. Nginx terminates TLS. Adapt the example vhost/domain and the matching allowedOrigin, WebSocket URL and origin check for your hostname.

Provide a private `secrets/` directory: access-policy.json (v5 schema shown in access-policy.example.json), auth-password-hashes.json (PBKDF2-SHA256), turn-key-hashes.json, shortlinks.json, obs-viewers.json and twilio.json. The latter contains your own Twilio accountSid/apiKeySid/apiKeySecret. No production data is included. JSON maps have version 1. Inspect turn-broker/server.js for the complete validation and session formats. Use scripts/room_wire_id.py to derive room wire IDs and stream suffix from your hostname and the frontend default password. Replace every placeholder in the example policy; talk stream IDs have the form ProdTalk plus 24 hex digits.

The scripts directory contains the original provisioning and migration code. Migration scripts are historical and are not an unattended fresh-install sequence; read their version checks first. Initial shortlink and OBS maps may be empty {"version":1,"links":{}} while you configure your own accounts and invitations. Credentials and map files must be readable by UID 10001; session-state must be writable by UID 10001. Keep them outside the frontend source directory and outside Git.

The source files use no frontend build step. Node and Caddy are pinned in the Dockerfiles. The signaling dependency ws is pinned in package-lock.json and its exact MIT-licensed source is included in vendor/ws. The original registry integrity hash is retained.

Source releases must be published before deploying changed code. scripts/verify-public-source.py verifies the runtime files against source-release.json, and deploy.sh runs it before recreating containers. Refresh that manifest only for a reviewed, published release.

The public Nginx and Compose files are examples: deployment-specific hostnames, certificate paths and bridge addresses are replaced with video.example.org and a sample 172.30.201.176/29 subnet. They are not the private production vhost. Update these settings consistently for your own installation.

## Sessions and access administration

Open /production-access and log in as Production. Select Joker and/or Creator accounts, confirm the change, and save the displayed list. New passwords remain available in the protected Production text-list download. Host/Production/Director credentials and other environments cannot be changed from this page. The old server-only access list does not update after rotations; use the newly downloaded list. Overrides include password hashes and authenticated encrypted export values in session-state/credentials.json. Keep this state and the private export key in protected backups; never replace the key during a normal deployment. Never copy session-state into the frontend or Git.

The nginx auth subrequest forwards the hashed session identifier to the private signaling server. Signaling polls turn-broker:8080/internal/active-sessions over the existing isolated bridge. Do not expose the broker or this internal endpoint directly. AUTH_BROKER_URL can configure the internal broker address. ALLOWED_ORIGIN configures the trusted browser origin in the two server components; it defaults to the production public hostname. BIND_HOST is optional for broker test fixtures; its container default is 0.0.0.0. No new public ports or writable secret mounts are required.

Reload all participant/Director pages and OBS browser sources once after deployment so receiver-side media revocation is active. Normal device changes remain supported: the latest login wins, and an older page cannot automatically reclaim that login. A person who still knows an unchanged password can log in again; rotate credentials after each event. Password rotation does not revoke already-issued third-party TURN credentials before their provider TTL.

Run the integration test with Node 24 and ws available on NODE_PATH: node deployment/tests/access-security.integration.js. It spawns only loopback fixture servers, uses generated temporary secrets, and removes them afterward.

## Default destinations and Production overview

Visiting the bare HTTPS domain routes through /home. Without a current session this serves the existing login form. After login, Host/Creator/Joker/return co-director accounts follow their existing personal shortlink. Production stays on the selection page with Test/Staging/Production main Director and Production-Talk entries, plus password administration. Existing explicit invitation and OBS viewer URLs retain their behavior. OBS collection accounts have a room-scoped source overview.

The broker serves /home, /api/navigation and /launch/director/{test,staging,production}. It reads only the existing private policy/shortlink/viewer maps, verifies a current session itself and checks the original entry policy before resolving a target. Nginx adds these application routes and a query-free root redirect; no new port, Docker network, account or secret file is required. home.html and navigation.js must be copied into the broker image. Restart only frontend and turn-broker, then test and gracefully reload Nginx; signaling does not need to restart.

## Complete access-list downloads

Log in as Production and open /production-access. The Test, Staging and Production download buttons produce separate text files with each room's complete user list, roles, personal links and OBS sources. The shared Production account appears in all three lists with only the chosen room's Director and Talk entries. Original passwords are included only while their verified fingerprint is still current. Newly rotated passwords are decrypted for subsequent exports. Legacy hash-only resets are marked unavailable until explicitly renewed once. Downloads do not rotate any password or revoke any session.

On the server, run scripts/prepare-account-downloads.py /path/to/private/secrets /path/to/new/protected/account-export.json. The output must not already exist. It verifies original plaintext passwords against the base salted hashes and writes only matching records with mode 0600. Review the count without printing the file, then install as secrets/account-export.json owned by the broker UID/GID 10001 with mode 0400. It is runtime-only secret data and must never be committed, included in source archives or copied into the frontend. The existing read-only /run/secrets mount is sufficient; ACCOUNT_EXPORT_FILE can override this path for isolated fixtures. If the optional file is absent, lists still contain all accounts and links, with missing passwords marked unavailable.

POST /api/production-access/export/{test,staging,production} requires the current Production session, the configured Origin and X-VDO-Action: download-access-list. GET and user-controlled room names are rejected. Existing password management remains restricted to Production Joker/Creator rotation. Reset passwords are retained only as authenticated encrypted export values alongside their login hashes; no plaintext reset password is written to disk.

## Private export encryption key

Create a new protected key file with scripts/prepare-password-export-key.py /path/to/new/password-export.key, then install as secrets/password-export.key with UID/GID 10001 and mode 0400. The script refuses to overwrite an existing key and prints no key material. Existing read-only secrets mounts and private writable session-state remain sufficient. PASSWORD_EXPORT_KEY_FILE selects a different key path for isolated tests. The key contains 64 lowercase hexadecimal characters (32 random bytes). Keep it together with credentials.json in protected backups; replacing or losing it makes existing encrypted export values unreadable. Do not publish either runtime file.

Deploying this version does not reset any account. To migrate old hash-only overrides, explicitly select only the affected Production Joker/Creator accounts in the existing management page, reset once and then download the full Production list. Such a reset disconnects those accounts and makes their previous passwords invalid. Test/Staging/Host/Production/Director passwords cannot be changed by this operation. Historical access-credentials.txt remains unchanged and is not the source for current reset passwords. Existing original passwords are still read from the verified optional account-export.json source, with current fingerprint checks.

The hash and ciphertext are stored in one atomic record, so a failed persistence write changes neither authentication nor export state. GCM associated data binds each export to its exact account/hash record. Missing keys block new rotations before mutation; corrupt or wrong-key encrypted values block exports rather than falling back to an obsolete original password. For an explicitly authorized migration, POST /api/production-access/renew-legacy with the Production cookie, same-origin Origin, X-VDO-Action: renew-legacy-exports and JSON {"confirm":"RENEW_LEGACY_EXPORTS"}. It selects only existing hash-only Production Joker/Creator overrides on the server, never accepts caller-supplied account names and becomes a no-op after migration. No startup or deployment calls this automatically. Runtime schema version 1 is retained and older hashes remain valid for authentication. Any rollback must preserve the current credentials.json and export key; an older broker does not support exporting encrypted reset values and may create hash-only values if used to rotate again.
